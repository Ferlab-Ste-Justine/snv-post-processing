# Ferlab-Ste-Justine/snv-post-processing: Output

## Introduction

This document describes the output produced by the pipeline.

The directories described below will be created in the output directory after the pipeline has finished.

For the vep and exomiser steps, it is possible to specify custom output directories via `vep_outdir` and `exomiser_outdir` parameters. If these parameters are not specified, the output for these steps will be included in the main output directory defined by the `outdir` parameter. Slivar output is always written under `outdir`.

Unless stated otherwise, this document assumes that the default output locations are used for vep and exomiser steps.

The pipeline output is saved step-by-step in the output directory as each step is completed. Below, we provide a description of the output folders corresponding to the main steps, as well as the `pipeline_info` folder, which contains details about the submitted job.

## Directory Structure

The output directory structure is as follows:

```
{outdir}
├── pipeline_info/
├── csv/
├── normalized_genotypes/
├── ensemblvep/
├── slivar/
├── exomiser/
...
```

The `pipeline_info` subdirectory contains details about the pipeline execution and metadata relevant to reproducibility, performance optimization and troubleshooting.

The `csv` subdirectory includes auto-generated index csv files for each of the analysis steps included. They keep the original output channel structure. They are used by the pipeline to further process/re-start from previously generated output.

The `normalized_genotypes` subdirectory contains the output after running GATK GenotypeGVCFs, splitting multi-allelics, and normalizing genotype ploidy (`bcftools +fixploidy`, forcing diploid GT notation on hemizygous non-PAR X/Y calls) and will appear if `save_genotyped = true`.

The `ensemblvep` subdirectory contains the output after running vep and will appear only if vep is specified in the `tools` parameters.

The `slivar` subdirectory contains the output of the slivar inheritance step. It will appear only if slivar is run (either by including `slivar` in the `tools` parameter alongside `vep`, or by setting `--step inheritance`) and at least one family in the samplesheet has a `familyPed` value.

The `exomiser` subdirectory contains the output after running exomiser and will appear only if exomiser is specified in the `tools` parameters.

## Output

By default, if vep, exomiser, and/or slivar are included as tools, **only annotated VCFs (ensemblvep), slivar inheritance results, and Exomiser results are published.** If no tools are included, the final joint-genotyped results are published.

If needed, you can set `save_genotyped` to `true` to publish the normalized joint-genotyping results or `publish_all` to `true` to publish the outputs from all pipeline steps. These outputs will be saved in subdirectories within the main output directory specified by the `outdir` parameter. The names of the subdirectories will match the nextflow process names.

> [!IMPORTANT]
> We don't recommend using `publish_all = true` in production. This is primarily useful for testing, debugging or troubleshooting.

## Pipeline Information: pipeline_info

Here we describe in more details the content of the `pipeline_info `subdirectory. It should contain the following:

```
|_ pipeline_info
   |_ configs
      |_ nextflow.config
          ...
   |_ execution_report_2024-12-09_12-03-20.html
   |_ execution_timeline_2024-12-09_12-03-20.html
   |_ execution_trace_2024-12-09_12-03-20.txt
   |_ params_2024-12-09_12-03-23.json
   |_ pipeline_dag_2024-12-09_12-03-20.html
   |_ snv-post-processing_software_mqc_versions.yml
   |_ metadata.txt
   |_ nextflow.log
```

The timestamps that appear in some files are in the user's timezone.

The `configs` folder contains copies of configuration files used. This includes the default `nextflow.config` file as well as any additional configuration files passed as parameters.

The files prefixed by `execution_`are reports automatically generated by nextflow. These reports allow you to troubleshoot errors with the pipeline execution and provide inofrmation such as launch commands, run times and resource usage. You can refer to the [nextflow documentation](https://www.nextflow.io/docs/latest/reports.html) for more details about these reports.

The file prefixed by `params` contains the parameters used by the pipeline.

The file prefixed by `pipeline_dag` contains a diagram of the pipeline steps.

The `snv-post-processing_software_mqc_versions.yml` file aggregates the software versions reported by every module/subworkflow that exposes a `versions` channel (bcftools, GATK4 sub-tools, VEP, exomiser, etc.) plus the pipeline and Nextflow versions. The format is MultiQC-friendly so it can be picked up by an external MultiQC step if/when one is wired in.

The `metadata.txt` file contains various information relevant for reproducibility, such as the original command line, the name of the branch / revision used, the username associated to the command, a list of configuration files passed, the nextflow work directory, etc.

The `nextflow.log` file is a copy the nextflow log file. Note that it will miss logs written after the `workflow.onComplete` handler is run.

## Annotation Step: ensemblvep

The `ensemblvep` subdirectory contains the output of the pipeline after the vep step.

```
|_ ensemblvep/
  |_ variants.family1.snv.vep.vcf.gz
  |_ variants.family1.snv.vep.vcf.gz.tbi
  ...
```

It contains one pair of `vcf.gz`, `vcf.gz.tbi` files per family. Specifically, we use the following naming scheme:

- `variants.<FAMILY_ID>.snv.vep.vcf.gz`
- `variants.<FAMILY_ID>.snv.vep.vcf.gz.tbi`

The family ID should match the family ID in the input sample sheet.

Note that, if vep is not specified in the `tools` parameter, the vep step will not be executed, and the `ensemblvep` subdirectory will not be created.

By default, VEP output is saved in the `ensemblvep` subfolder within the main output directory. To save the output to a different location, use the `vep_outdir` parameter.
In this case, the .vcf.gz and .vcf.gz.tbi files will be saved at the root of the specified location.

## Slivar Step: slivar

The `slivar` subdirectory contains the output of the slivar inheritance subworkflow, which runs per family after VEP when slivar is enabled and a `familyPed` is provided in the samplesheet.

```
|_ slivar/
   |_ variants.family1.snv.vep.slivar.vcf.gz
   |_ variants.family1.snv.vep.slivar.vcf.gz.tbi
   |_ family1.expr.slivar.summary.txt
   |_ family1.ch.slivar.summary.txt
   ...
```

For each family, the directory contains:

- `variants.<FAMILY_ID>.snv.vep.slivar.vcf.gz` and `.vcf.gz.tbi`: the VEP-annotated VCF re-annotated with the slivar inheritance tags (see below) and the compound-het annotation (`slivar_comphet`). The intermediate `comphet_side`/`het_side`/`denovo_side` INFO fields used to drive compound-het detection are stripped from the published file.
- `<FAMILY_ID>.expr.slivar.summary.txt`: per-expression hit counts emitted by `slivar expr`.
- `<FAMILY_ID>.ch.slivar.summary.txt`: per-expression hit counts emitted by `slivar compound-hets`.

The family ID should match the family ID in the input sample sheet.

### Inheritance tags

Each variant in the published VCF may carry one or more `INFO` tags listing the affected sample(s) for which the mode-of-inheritance (MoI) rule passed. The rules themselves live in [`assets/slivar-functions.js`](../assets/slivar-functions.js) and are wired up in [`conf/slivar.config`](../conf/slivar.config); they are designed to be biological-evidence honest, i.e. a tag fires only when the family genotypes + structure actually support the inference. The MoI tags are named after the values Radiant uses for `transmission_mode`, except `uniparental_disomy`, which has no Radiant equivalent.

Every tag below except `slivar_comphet`, and the unknown-genotype and parental-origin tags further down, is evaluated on every variant that passes slivar's pre-filter: `PASS`, not a `*` allele, and, when the gnotate files are provided, rare by `gnomad_popmax_af_rare` / `topmed_af_rare`. The variant's consequence doesn't matter, so synonymous, intronic, UTR, upstream/downstream and intergenic variants are tagged too, as in the Radiant ETL. Compound hets are the exception: only variants slivar considers impactful (its `INFO.impactful` flag, derived from the VEP consequence: loss-of-function, missense, inframe and splice-region variants) can be one side of a `slivar_comphet` pair.

| Tag                         | When it fires                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Family structure required                                                                                                                                                       |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `autosomal_dominant_denovo` | Affected proband is het; both parents in PED are hom-ref. Self-gates to trios because the rule requires both parents in the sample.                                                                                                                                                                                                                                                                                                                                                    | Trio (proband has both parents sequenced)                                                                                                                                       |
| `autosomal_recessive`       | Affected proband hom-alt; **every unaffected parent is het** (strict carrier rule rejects Mendelian violations); unaffected siblings can be het or hom-ref.                                                                                                                                                                                                                                                                                                                            | Trio, nuclear, duo, or single-parent + sib. **Not solos** — a solo provides no segregation evidence.                                                                            |
| `autosomal_dominant`        | Affected = het or hom-alt; unaffected = hom-ref; **at least one affected parent has children in the family** (gates out de novos which would otherwise match the same genotype pattern).                                                                                                                                                                                                                                                                                               | Trio with affected parent, nuclear with affected parent, or duo with affected parent                                                                                            |
| `uniparental_disomy`        | Affected proband hom-alt; **exactly one parent is hom-ref** (the other carries the allele). Diagnostic of uniparental disomy / parental deletion in trans / somatic mosaicism.                                                                                                                                                                                                                                                                                                         | Trio only — needs both parents to detect the Mendelian violation                                                                                                                |
| `x_linked_dominant_denovo`  | Sex-aware de novo on chrX in an affected **daughter** (het). Self-gates to trios via the parent-presence check in `segregating_denovo_x`.                                                                                                                                                                                                                                                                                                                                              | Trio                                                                                                                                                                            |
| `x_linked_recessive_denovo` | Sex-aware de novo on chrX in an affected **son** (hemizygous). Same rule as `x_linked_dominant_denovo`; only the child's sex differs. Affected siblings of both sexes sharing the de novo would set both tags.                                                                                                                                                                                                                                                                         | Trio                                                                                                                                                                            |
| `x_linked_recessive`        | Sex-aware X-linked recessive. Affected male = hom-alt (hemizygous); affected female = hom-alt.                                                                                                                                                                                                                                                                                                                                                                                         | Trio, nuclear, duo, or single-parent + sib. **Not solos**. Note: a duo with mom and male proband is sufficient — mom is the only relevant transmission source on chrX for sons. |
| `x_linked_dominant`         | Sex-aware X-linked dominant with the same affected-parent gate as `autosomal_dominant`.                                                                                                                                                                                                                                                                                                                                                                                                | Trio or duo with affected parent                                                                                                                                                |
| `slivar_comphet`            | Two same-gene heterozygous variants in an affected proband, paired by `slivar compound-hets`. In trios, the per-variant `comphet_side` upstream input enforces transmission asymmetry (one variant from each parent); in non-trios, the `het_side` input flags any hq het in the proband (cis vs. trans is unresolvable without both parents). An impactful `autosomal_dominant_denovo` variant can also pair with an inherited het in the same gene. Both variants must be impactful. | Any structure with a het proband (trio comphet has transmission proof; non-trio comphet is a candidate)                                                                         |
| `candidate`                 | Set **alongside** an MoI tag when family structure cannot prove segregation. Fires only for: (a) `autosomal_recessive` in non-trio families, (b) `x_linked_recessive` in non-trio families _except_ duo-with-mom for a male proband. Non-trio `slivar_comphet`s are also unprovable but the `candidate` flag is **not** auto-applied to them (would require a post-compoundhets pass) — treat any `slivar_comphet` in a non-trio family as a candidate by convention.                  | Non-trio families with an unprovable single-variant MoI                                                                                                                         |

### How structure affects what fires

Slivar treats each family independently. The same variant can fire different tags in different families depending on the PED:

| Family structure                    | Tags that can fire                                                                                                                                                                                                                                                                                                                    |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Trio (mom + dad + affected proband) | All of: `autosomal_dominant_denovo`, `autosomal_recessive`, `autosomal_dominant`, `x_linked_dominant_denovo`, `x_linked_recessive_denovo`, `x_linked_recessive`, `x_linked_dominant`, `uniparental_disomy`, `slivar_comphet`. No `candidate` — segregation is provable.                                                               |
| Nuclear (trio + unaffected sibs)    | Same as trio; siblings provide additional segregation evidence through `fam.every`.                                                                                                                                                                                                                                                   |
| Duo with affected parent            | `autosomal_dominant`, `x_linked_dominant` confirmed (transmission visible). `autosomal_recessive`, `x_linked_recessive` (if applicable) fire with `candidate` (other parent's carrier status not verified).                                                                                                                           |
| Duo with unaffected parent          | `autosomal_recessive` + `candidate` when proband hom-alt + parent het. `x_linked_recessive` confirmed (no `candidate`) when mom + male proband. `slivar_comphet` for paired hets (treat as candidate by convention since family is non-trio). The de novo tags and `autosomal_dominant` do not fire (no segregation evidence).        |
| Single-parent + sib(s)              | Same as duo: `autosomal_recessive`/`x_linked_recessive` + `candidate`, `slivar_comphet` (treat as candidate). Siblings contribute to `fam.every` checks.                                                                                                                                                                              |
| Solo / sibship (no parents in PED)  | Only `slivar_comphet` can fire (from a pair of hets in the proband; treat as candidate), plus `unknown_parents_genotype` on every variant. Single-variant `autosomal_recessive`/`x_linked_recessive` are intentionally **suppressed** by the `no_parents_in_fam(fam)` gate — neither solos nor sibships provide segregation evidence. |
| Sibship (no parents)                | Like a solo from slivar's perspective — no parental data to segregate against.                                                                                                                                                                                                                                                        |

### When two MoI tags fire together

Each MoI rule is evaluated on its own, so a variant whose genotypes fit two modes gets both tags. Radiant's `transmission_mode` holds a single value, so the downstream consumer has to choose. In a trio this happens in four configurations (A = affected, U = unaffected):

| #   | Tags                                               | Child        | Father  | Mother  | Radiant's value for these genotypes | Why both fire                                                                                                                                                 |
| --- | -------------------------------------------------- | ------------ | ------- | ------- | ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `autosomal_recessive` + `autosomal_dominant`       | 1/1 (A)      | 1/1 (A) | 1/1 (A) | `autosomal_recessive`               | Nobody is het, so nothing shows whether one copy is enough. Recessive (pseudo-dominance) is the likelier reading.                                             |
| 2   | `x_linked_recessive` + `x_linked_dominant`         | 1/1 (A, son) | 1/1 (A) | 0/0 (U) | `x_linked_recessive`                | Affected father and son, no affected females.                                                                                                                 |
| 3   | `autosomal_dominant` + `uniparental_disomy`        | 1/1 (A)      | 0/1 (A) | 0/0 (U) | none                                | The phenotype follows the affected parent; the child's second alt allele has no parental source. The parents can be swapped, and the affected one can be 1/1. |
| 4   | `x_linked_recessive_denovo` + `x_linked_recessive` | 1/1 (A, son) | 0/0 (U) | 0/0 (U) | `x_linked_recessive_denovo`         | Every de novo X variant in an affected son: `x_linked_recessive` accepts an unaffected hom-ref mother.                                                        |

Cases 1 and 2 also occur in a duo with only the affected parent sequenced, together with `candidate` and an `unknown_*_genotype` tag. Each tag lists every affected member of the family, so an affected parent appears in it alongside the child. These cases are covered by the `SLIVAR_INHERITANCE` nf-test (`subworkflows/local/slivar_inheritance/tests/`).

### Unknown-genotype tags

Five more tags record why a family or a child can't be given a mode of inheritance. Their names are the values Radiant uses for `transmission_mode`, so downstream tools can map them directly. They are set **alongside** any MoI tag rather than replacing it: a duo can carry `autosomal_recessive` + `candidate` and `unknown_father_genotype` on the same variant, and choosing which one to report is left downstream.

| Tag                        | When it fires                                                                                                                                                                             | Evaluated                                         |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- |
| `unknown_parents_genotype` | No member of the family has a child in it: solos and sibships. Radiant itself never returns this value, because it only computes a transmission mode when at least one parent is present. | Per family; lists its affected sample(s)          |
| `unknown_father_genotype`  | The family has a mother but no father in the VCF, including when the PED names a father who wasn't sequenced.                                                                             | Per family; lists its affected sample(s)          |
| `unknown_mother_genotype`  | The family has a father but no mother in the VCF.                                                                                                                                         | Per family; lists its affected sample(s)          |
| `non_carrier_proband`      | The child is hom-ref.                                                                                                                                                                     | Per child with both parents in the VCF (`--trio`) |
| `unknown_proband_genotype` | The child has no call, or a call backed by only 1–2 reads of the called allele (the same low-depth rule as the parental-origin tags).                                                     | Per child with both parents in the VCF (`--trio`) |

"Unknown" parent means not sequenced. A parent who is in the VCF but has no call at the site doesn't trigger these tags; the `po_possible_*` tags below cover that case. The three family-level tags describe the family, not the variant, so they are set on every variant that passes slivar's pre-filter (`PASS`, and rare when the gnotate files are provided). The two child-level tags only ever fire in complete trios, because a missing parent takes precedence over the child's genotype.

### Parental origin tags

Every child with at least one parent in the VCF (trios and duos) gets at most one parental-origin `INFO` tag on each variant it carries, computed by `parental_origin()` in [`assets/slivar-functions.js`](../assets/slivar-functions.js) and wired up via the `--sample-expr` expressions in [`conf/slivar.config`](../conf/slivar.config). In a duo, the parent who wasn't sequenced counts as unknown, as in Radiant, so the duo labels are the ones a trio gets when that parent has no call (mostly `po_possible_*`). A child who is hom-ref, or whose genotype is unknown, gets no parental-origin tag; `non_carrier_proband` / `unknown_proband_genotype` (trios) or the family's `unknown_*_genotype` tag (duos) says why instead. Solos, sibships and the parents themselves get no parental-origin tag.

> [!NOTE]
> A parent who wasn't sequenced must be written as `0` in the PED, and the pipeline stops before slivar if a sequenced child's PED names a parent who isn't in the VCF. slivar mishandles such a family: when the father is the one missing, it drops the child's link to the mother as well, so the child would look parentless and get no parental-origin tags. See the PED requirements in [usage.md](usage.md#samplesheet-input).

| Tag                  | Meaning                                                                                                                                                                                    |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `po_denovo`          | Neither parent's genotype explains the proband's alt allele(s) — apparent de novo variant.                                                                                                 |
| `po_mother`          | The proband's alt allele(s) are explained by the mother's genotype alone.                                                                                                                  |
| `po_father`          | The proband's alt allele(s) are explained by the father's genotype alone.                                                                                                                  |
| `po_both`            | The proband is hom-alt and both parents carry the alt allele — origin cannot be narrowed further.                                                                                          |
| `po_ambiguous`       | Both parents' genotypes are consistent with having transmitted the allele; origin can't be resolved.                                                                                       |
| `po_possible_denovo` | One parent is hom-ref and the other is unknown (no call, or not sequenced) — de novo is possible but not confirmed.                                                                        |
| `po_possible_mother` | The mother's genotype is consistent with transmission, but the father's genotype is unknown (no call, or not sequenced).                                                                   |
| `po_possible_father` | The father's genotype is consistent with transmission, but the mother's genotype is unknown (no call, or not sequenced).                                                                   |
| `po_unknown`         | The child carries the variant, but the parents' genotypes can't resolve where it came from — for example, neither parent has a usable call (no call, or a call resting on only 1–2 reads). |

Origin is resolved separately depending on the variant's location: autosomal and pseudoautosomal (PAR) sites use one lookup table (proband, father, and mother all diploid); non-PAR X and Y sites use sex-aware tables that account for male hemizygosity. This requires genotypes to be in diploid GT notation — see the [ploidy normalization note](usage.md#starting-with-normalization---step-normalize) in the usage docs, which this tagging depends on for callers (e.g. DRAGEN) that emit true haploid calls on non-PAR X/Y.

### Notes

- The `candidate` flag is independent of the AF / rarity filter — it describes _structural_ uncertainty, not population rarity. Downstream tooling can treat `INFO/candidate=<sample>` as a "lower-confidence than trio-confirmed" breadcrumb.
- A single-variant `uniparental_disomy` match is **suggestive but not diagnostic** — true UPD shows up as a _cluster_ of these patterns across a chromosome. Cluster-level confirmation is a downstream task.
- The `autosomal_dominant` and `x_linked_dominant` rules require an affected parent. A trio with two unaffected parents + affected proband het fires `autosomal_dominant_denovo` but not `autosomal_dominant`, by design (otherwise every de novo would double-tag).
- The `autosomal_recessive` rule rejects Mendelian violations: if both parents are hom-ref and the proband is hom-alt, no tag fires (this is data-quality or CNV territory, not recessive inheritance).
- Compound-het detection uses two parallel paths: `--trio comphet_side(kid, mom, dad)` for trios (transmission-aware, also rejects variants where either parent is hom-alt) and `--family-expr moi_het_side(fam)` for everything else (rejects only variants where the present parent is hom-alt). Both feed the same `slivar compound-hets` pairing step, together with `denovo_side` (the impactful `autosomal_dominant_denovo` variants). All three inputs are restricted to impactful variants in `conf/slivar.config`: `slivar compound-hets` skips intronic, UTR, upstream/downstream and intergenic consequences by itself, but not synonymous ones, which would otherwise pair.

> [!NOTE]
> If slivar is not enabled (via the `tools` parameter or `--step inheritance`), or if no family in the samplesheet has a `familyPed` value, the slivar step will not be executed and the `slivar` subdirectory will not be created.

Slivar output is always written to the `slivar` subfolder within the main output directory.

## Exomiser Step: exomiser

The `exomiser` subdirectory contains the output fo the pipeline after the exomiser step.

```
|_ exomiser
   |_ family1.exomiser.genes.tsv
   |_ family1.exomiser.html
   |_ family1.exomiser.json
   |_ family1.exomiser.variants.tsv
   |_ family1.exomiser.vcf.gz
   |_ family1.exomiser.vcf.gz.tbi
  ...
```

It should contains a set of 6 files per family. Specifically, we use the following naming scheme:

- `<FAMILY_ID>.exomiser.genes.tsv`
- `<FAMILY_ID>.exomiser.html`
- `<FAMILY_ID>.exomiser.json`
- `<FAMILY_ID>.exomiser.variants.tsv`
- `<FAMILY_ID>.exomiser.vcf.gz`
- `<FAMILY_ID>.exomiser.vcf.gz.tbi`

The family ID should match the family ID in the input sample sheet.

For more details about the content of each of these files, you can have a look at the exomiser documentation [here](https://exomiser.readthedocs.io/en/latest/result_interpretation.html)

> [!NOTE]
> If exomiser is not specified in the `tools` parameter, the exomiser step will not be executed, and the `exomiser` subdirectory will not be created.

By default, exomiser output is saved in the `exomiser` subfolder within the main output directory. To save the output to a different location, use the `exomiser_outdir` parameter. In this case, the exomiser files will be written at the root of the specified location.
